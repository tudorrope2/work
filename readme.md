# ⚡ 실시간 멀티 타이핑 아레나 (Real-time Multi-Typing Arena)

Python(Flask)과 Socket.IO를 기반으로 여러 사용자가 동일한 방(Room)에 접속해 실시간으로 한글 문장 타이핑 속도와 정확도를 겨루는 멀티플레이어 웹 애플리케이션입니다. Docker와 Docker Compose를 활용해 개발 환경과 배포 환경을 컨테이너로 일원화했으며, AWS EC2(Ubuntu) 서버에 구축하여 외부 사용자가 웹 브라우저만으로 즉시 접속해 대결할 수 있도록 구성했습니다.

---

## 1. 서비스 소개

### 🎯 대상 사용자
* 혼자서 정해진 문장을 반복 입력하는 기존 타자 연습 방식에 지루함을 느끼고, 친구·동료와 실시간으로 속도와 순위를 겨루고 싶은 사용자
* 별도의 클라이언트 프로그램이나 폰트·패키지 설치 없이 웹 브라우저 주소(URL) 공유만으로 가볍게 미니게임을 즐기고 싶은 사용자

### 💡 해결하려는 문제 (기획 배경)
* **단방향 타자 연습의 한계 극복:** 기존 웹 타자 연습 서비스는 대부분 개인 기록 측정에 그쳐 경쟁 요소가 부족했습니다. 이를 해결하기 위해 WebSocket 양방향 통신을 도입하여 방에 참여한 모든 유저의 입력 진척도(`%`)를 실시간 프로그레스 바로 시각화했습니다.
* **멀티플레이 환경의 상태 충돌 및 부정 입력 방지:** 여러 명이 동시에 접속하는 환경에서 게임 도중 다른 참가자가 시작 버튼을 눌러 문장이 초기화되는 문제와, 오타를 낸 상태로 계속 타이핑해 진척도가 올라가는 문제를 해결하여 공정한 실시간 대결 경험을 제공합니다.

### ✨ 핵심 기능
* **방(Room) 기반 실시간 멀티플레이 및 세션 관리:**
  * 닉네임과 방 코드를 입력해 독립된 게임 세션에 입장할 수 있으며, 방에 접속 중인 참가자 목록이 실시간으로 동기화됩니다.
  * 우측 상단의 **`🚪 메인으로 나가기`** 버튼을 통해 언제든 로비로 복귀할 수 있으며, 퇴장 즉시 서버 메모리에서 해당 유저의 세션과 진척도 바가 정리됩니다.
* **실시간 타수(CPM)·정확도(%) 계산 및 글자 단위 피드백:**
  * 타이핑 시작 시점부터 경과 시간을 분 단위로 환산해 실시간 분당 타수(CPM)와 정확도(`%`)를 상단에 표시합니다.
  * 입력 상태에 따라 **정답 글자(초록색 배경)**, **오타 발생(빨간색 배경 경고 및 진척도 증가 중단)**, **현재 입력 커서 위치(하늘색 밑줄)**를 즉각적으로 렌더링합니다.
* **중복 시작 방지 및 상태 제어:**
  * 방의 누군가가 `게임 시작` 버튼을 누르면 서버에서 해당 방의 상태를 진행 중(`is_playing = True`)으로 잠그고, 모든 참가자 화면에서 시작 버튼을 숨겨 플레이 도중 의도치 않은 게임 초기화를 차단합니다.
* **실시간 완주 결과 모달(Modal) 및 라운드 재시작:**
  * 한 참가자가 문장을 완주하면 본인과 상대방 화면 정중앙에 **완주 결과 팝업(최종 타수 및 정확도)**이 실시간 브로드캐스트로 표시됩니다.
  * 결과 팝업의 `확인` 버튼을 누르면 하단에 **`🔄 게임 재시작`** 버튼이 활성화되어 다음 라운드를 연속으로 진행할 수 있습니다.

## 2. AWS 아키텍처 구성도

### 🔄 사용자 요청 및 데이터 흐름 경로

    [사용자 웹 브라우저 (Client)]
           │
           │  1. 초기 페이지 로드: HTTP GET (Port: 8080)
           │  2. 실시간 게임 이벤트: WebSocket / Socket.IO (Port: 8080)
           ▼
    [AWS VPC & 보안 그룹 (Security Group)]
           │  * 인바운드 규칙: TCP 8080 (웹/소켓 트래픽), TCP 22 (SSH 관리) 허용
           ▼
    [AWS EC2 인스턴스 (Ubuntu Linux)]
           │  * Docker Engine & Docker Compose 구동
           │  * 호스트 8080 포트 ──▶ 컨테이너 5000 포트 포워딩 (8080:5000)
           ▼
    [Docker 컨테이너 (work-web-1)]
           │
           ▼
    [Python Flask + Flask-SocketIO 서버 (Port: 5000)]
           │  * 정적 템플릿 렌더링 (templates/index.html)
           │  * 인메모리 방 상태 관리 (rooms 딕셔너리: 참가자, 진척도, 진행 여부)

### ☁️ 사용한 AWS 서비스의 역할 및 선택 이유
* **AWS EC2 (Elastic Compute Cloud - Ubuntu):**
  * **역할:** Docker 컨테이너를 실행하고 Python Flask-SocketIO 백엔드 서버를 상시 호스팅하는 가상 컴퓨팅 인스턴스입니다.
  * **선택 이유:** 본 서비스는 `Socket.IO`를 이용해 클라이언트와 서버 간 지속적인 양방향 통신(Stateful WebSocket 연결)을 유지해야 합니다. 요청이 들어올 때만 일시적으로 실행되는 서버리스 컴퓨팅(AWS Lambda 등)은 지속적인 소켓 연결 유지에 제약이 있으므로, 상시 구동되며 네트워크 포트와 컨테이너 환경을 자유롭게 제어할 수 있는 EC2를 선택했습니다.
* **AWS VPC 및 보안 그룹 (Security Group):**
  * **역할:** EC2 인스턴스 앞단에서 인바운드·아웃바운드 트래픽을 필터링하는 가상 방화벽 역할을 수행합니다.
  * **선택 이유:** 외부 사용자가 웹 애플리케이션에 접근할 수 있도록 서비스 포트(`TCP 8080`)만 개방하고, 서버 유지보수를 위한 원격 접속(`TCP 22`) 외의 불필요한 포트는 모두 차단하여 최소 권한 원칙에 따른 기본적인 네트워크 보안을 확보했습니다.

## 3. 실행·배포 방법

### 🛠️ 사전 준비 사항 (Prerequisites)
* **로컬 개발 환경:** Python 3.9 이상, `pip` 패키지 관리자, Git
* **AWS 배포 환경:** AWS EC2(Ubuntu) 인스턴스, Docker 및 Docker Compose 설치, EC2 보안 그룹 인바운드 규칙에 `TCP 8080` 포트 추가

### 📂 프로젝트 디렉터리 구조

    work/
    ├── app.py                  # Flask 라우팅 및 Socket.IO 이벤트 핸들러 (join, leave, start_game, user_progress, finish_game)
    ├── templates/
    │   └── index.html          # Light 테마 프론트엔드 UI, 실시간 오타 검증 스크립트, 완주 결과 모달 팝업
    ├── Dockerfile              # Python 3.9 기반 애플리케이션 이미지 빌드 명세
    ├── docker-compose.yml      # 컨테이너 실행 설정 및 포트 포워딩 (8080:5000) 정의
    └── README.md               # 프로젝트 개요, 아키텍처, 배포 가이드 및 확장 검토 문서

### 💻 로컬 단독 실행 명령 (Docker 미사용 시)
1. GitHub 저장소 클론 및 프로젝트 폴더 이동

       git clone <GitHub_Repository_URL>
       cd work

2. 필수 파이썬 패키지 설치 및 서버 실행

       pip install flask flask-socketio
       python app.py

3. 로컬 브라우저 접속: `http://localhost:5000/`

### 🚀 AWS EC2 배포 및 업데이트 절차 (Docker Compose)
1. **로컬 PC에서 수정한 코드를 GitHub 원격 저장소에 푸시**

       git add -A
       git commit -m "기능 업데이트 및 UI 개선"
       git push origin main

2. **AWS EC2 터미널 접속 후 최신 코드 반영 및 컨테이너 재빌드**

       cd ~/work
       git pull origin main
       sudo docker compose down
       sudo docker compose build --no-cache
       sudo docker compose up -d

3. **컨테이너 정상 구동 여부 확인**

       sudo docker ps

   *(출력 결과의 `STATUS`가 `Up` 상태이고, `PORTS`에 `0.0.0.0:8080->5000/tcp`가 표시되면 정상 배포 완료)*

### 🌐 포트 구성 및 외부 접속 주소
* **외부 서비스 접속 주소:** `http://<EC2_퍼블릭_IPv4_주소>:8080/`
* **포트 매핑 구조:**
  * 외부 클라이언트 요청은 EC2 보안 그룹의 **`8080`번 포트**로 유입되며, `docker-compose.yml`의 포트 설정(`8080:5000`)을 통해 호스트의 `8080`번 포트가 Docker 컨테이너 내부 Flask-SocketIO 서버의 **`5000`번 포트**로 전달됩니다.

## 4. 트러블슈팅 및 개발 개선 이력

1. **초기 로드 시 완주 팝업 노출 및 오타 판정 버그 해결:**
   * 페이지 진입 직후 모달 창이 노출되던 현상을 해결하기 위해 CSS에 `.hidden { display: none !important; }` 규칙을 명시하고, 게임 시작 전 빈 문자열 상태에서는 완주 판정이 실행되지 않도록 조건문을 보강했습니다.
   * 오타가 발생한 글자 이후로는 `correctCount` 집계를 중단시켜, 오타를 수정해야만 진척도(`%`)가 올라가도록 판정 정확도를 높였습니다.
2. **정적 템플릿 캐싱 및 경로 오류(`TemplateNotFound`) 해결:**
   * 템플릿 파일명 변경 과정에서 발생한 `jinja2.exceptions.TemplateNotFound` 오류를 해결하기 위해 `templates/index.html` 단일 구조로 통일하고, 배포 시 `docker compose build --no-cache`와 브라우저 강력 새로고침(`Ctrl + F5`)을 적용해 최신 UI가 즉시 반영되도록 조치했습니다.
3. **멀티플레이 UX 및 방 생명주기 관리 개선:**
   * 게임 진행 중 타인의 시작 버튼 클릭으로 라운드가 리셋되는 문제를 막기 위해 `is_playing` 상태 플래그를 도입하고 시작 버튼을 숨김 처리했습니다.
   * 방 입장 시 초기 버튼 텍스트(`게임 시작`)와 라운드 종료 후 모달 확인 시 버튼 텍스트(`🔄 게임 재시작`)를 `hasPlayedOnce` 변수로 명확히 분리했으며, 로비로 복귀할 수 있는 `🚪 메인으로 나가기` 기능을 추가했습니다.

## 5. 확장 검토 (ELB & Auto Scaling)

### 📌 현재 적용 여부: **미적용 (단일 EC2 인스턴스 + Docker Compose 운영)**

### 🔍 기술적 판단 근거
1. **Stateful(상태 유지) 인메모리 구조와의 충돌:**
   * 현재 백엔드 서버는 방별 접속자 목록, 실시간 진척도, 게임 진행 여부를 Python 프로세스 내부의 **인메모리 딕셔너리(`rooms = {}`)**에 저장하고 있으며, `Socket.IO`를 통해 클라이언트와 지속적인 WebSocket 연결을 유지합니다.
   * 만약 현재 구조 그대로 **Elastic Load Balancing(ALB)**과 **Auto Scaling**을 적용해 EC2 인스턴스가 2대 이상으로 수평 확장(Scale-out)되면, 동일한 방 코드(`room1`)로 접속한 사용자들이 서로 다른 인스턴스로 분산 라우팅됩니다. 이 경우 각 인스턴스가 독립된 메모리를 가지므로 **참가자 목록이 보이지 않거나 실시간 진척도가 동기화되지 않는 상태 불일치(State Inconsistency) 문제**가 발생합니다.
2. **예상 트래픽 규모 및 비용 효율성:**
   * 소규모 그룹 단위의 실시간 타자 대결을 목적으로 하는 서비스 특성상 단일 EC2 인스턴스만으로도 동시 접속자 트래픽을 충분히 처리할 수 있습니다. 상시 비용이 발생하는 로드밸런서(ALB)와 다중 인스턴스를 운영하지 않음으로써 인프라 유지 비용을 최소화했습니다.

### 🚀 향후 대규모 트래픽 대응을 위한 아키텍처 개선 방안
서비스 규모가 커져 **ELB(Application Load Balancer)와 Auto Scaling을 도입해야 할 경우**, 다음과 같은 아키텍처 전환을 통해 무상태(Stateless) 확장이 가능하도록 개선할 수 있습니다.

1. **외부 인메모리 데이터 저장소 도입 (AWS ElastiCache for Redis):**
   * 각 EC2 인스턴스 메모리에 저장하던 방 상태(`rooms`) 데이터를 외부 **Redis**로 분리하여 모든 인스턴스가 동일한 방 상태를 공유하도록 변경합니다.
   * `Flask-SocketIO`에 Redis 메시지 큐(`message_queue='redis://...'`)를 연동하여, 서로 다른 인스턴스에 연결된 사용자 간에도 실시간 진척도와 완주 이벤트가 정상적으로 브로드캐스트되도록 구성합니다.
2. **ALB Sticky Session(고정 세션) 설정:**
   * Socket.IO의 초기 HTTP Long-Polling 핸드셰이크 과정에서 요청이 다른 인스턴스로 튀어 연결이 끊어지는 현상을 방지하기 위해, ALB 대상 그룹(Target Group)의 **고정 세션(Stickiness)** 옵션을 활성화합니다.
